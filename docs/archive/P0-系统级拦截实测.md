# P0 系统级拦截实测记录

日期：2026-10-29
环境：Android15 AVD（Pixel 7 / API 35，AOSP 原生），Gradle 8.9 + AGP 8.7.3

## 背景

需求要求浮窗期间「不可侧滑或上滑返回桌面」。纯应用层无法拦截全面屏手势，因为手势由系统
InputDispatcher 在浮窗之下处理。评估阶段的结论是：唯一可行的系统级手段是通过 Shizuku 以
shell 身份执行 LockTask，其可用性属于 P0 最高风险项，必须先于 UI 开发验证。

## 结论：可用

`am task lock <taskId>` 在 Android 15 上通过 adb（即 shell 权限，uid 2000）执行成功，
当前前台任务被置于 LockTask（`mLockTaskModeState=PINNED`）状态。实测拦截效果：

| 操作 | 未锁定 | 锁定后 |
|---|---|---|
| `input keyevent KEYCODE_BACK` | 退出应用 | 被拦截，停在原应用 |
| `input keyevent KEYCODE_HOME` | 回桌面 | 被拦截，停在原应用 |
| 左边缘右滑（手势返回） | 回上一级 | 被拦截，停在原应用 |
| 底部上滑（手势回桌面） | 回桌面 | 被拦截，停在原应用 |

无需 root，无需 Device Owner，无需 `dpm set-device-owner`。这是本项目方案成立的关键前提。

## 命令用法

```bash
# 取得当前前台任务 ID（注意 t7 是 task id，不是 activity stack id）
adb shell dumpsys activity activities | grep -i topResumedActivity
# 形如：topResumedActivity=ActivityRecord{... com.android.settings/... t7}

# 锁定
adb shell am task lock 7

# 解除
adb shell am task lock stop
```

## 注意事项

1. **必须先取到 taskId**。传入空值会静默失败且没有任何提示，实测中因此误判过一次。
2. `am task lock stop` 在未锁定状态下会打印 `Activity manager is not in lockTaskMode`，
   这是正常提示，不是错误。
3. **异常未解除会导致设备停留在锁定态**。因此 P1 集成时必须配套独立看门狗：锁定时把到期
   时间戳落盘，由独立进程的定时任务到点无条件执行 stop，不依赖主进程存活。
4. 本结论在 AOSP 原生系统上取得。澎湃OS4 属深度定制，需在真机上重复同一组验证，作为
   接入 Shizuku 前的准入条件。

## 与浮窗的关系

LockTask 负责系统级拦截（手势、Home、状态栏下拉），应用层浮窗负责视觉呈现与倒计时。
两者叠加：即便 LockTask 在某 ROM 上被削弱，浮窗仍能遮挡视觉并消费触摸。
