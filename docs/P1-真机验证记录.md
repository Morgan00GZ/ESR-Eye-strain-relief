# P1 真机验证记录

日期：2026-10-30
设备：25098PN5AC / Android 17（SDK 37）/ HyperOS OS4.0
权限条件：ADB 调试 + Shizuku（已授权本应用）

## 一、系统级锁定：确认可用

在澎湃OS4 上以 shell 身份执行 `am task lock <taskId>`，系统进入
`mLockTaskModeState=PINNED`。实测拦截效果：

| 操作 | 结果 |
|---|---|
| 返回键 | 被拦截，停在原应用 |
| Home 键 | 被拦截，停在原应用 |
| 底部上滑回桌面 | 被拦截 |
| 左边缘侧滑返回 | 被拦截 |
| 状态栏下拉 | 焦点被夺，无法展开 |

结论：**无需 root、无需 Device Owner**，方案的硬约束在真机上得到满足。

## 二、Shizuku 集成：端到端跑通

- 授权流程正常，Shizuku 弹窗「始终允许」后可执行命令。
- 浮窗弹出后自动锁定当前任务（实测 taskId=42，锁定对象为本应用）。
- 浮窗期间注入返回键与 Home 键，前台 Activity 不变，拦截生效。
- 倒计时结束自动执行 `am task lock stop`，状态回到 `NONE`。

### 实现要点

1. Shizuku 13.x 的 `newProcess` 被设为私有，编译期不可见，改用反射获取，
   避免降级依赖版本。
2. 锁定是异步的：浮窗先上屏，再在后台线程取 taskId 并执行锁定，
   避免两条 shell 命令的几百毫秒延迟拖慢视觉反馈。
3. 锁定同时登记 35 秒后的看门狗闹钟（浮窗时长 +15 秒），由 AlarmManager
   托管，不依赖应用进程存活；浮窗正常结束则取消。
4. `unlock` 幂等，计时服务每次启动都无条件执行一次，自愈上次异常退出可能
   残留的锁定态。

## 三、注视数据源：当前不可用

探测结论（均为实测）：

- 无任何 gaze / attention / presence 类传感器。
- 系统存在 `attention` 服务（`android.attention.IAttentionManager`），
  实现者为 `com.xiaomi.aon` 的 `AonAttentionService`，`isServiceEnabled=true`。
- `dumpsys attention` 可读到历史上最多 5 条判定缓存（`result=1` 注视 / `result=0` 未注视）。
- **缓存只在屏幕即将熄灭前才刷新**：40 秒内条目数保持 5 条不变，说明这是
  按需触发的事件型信号，不是连续数据流。
- `service call attention` 各 transaction 均返回 `Not a data message`，
  无可用只读接口；第三方与 shell 均无法主动触发检测。

对需求的影响：注视时长的核心前提是「能持续得知用户是否在看屏幕」，而该机型
只提供极稀疏的瞬时判定，无法支撑 20 分钟累计。因此 **注视计时暂不实现**，
应用当前走亮屏计时分支（架构上本就是注视源不可用时的默认路径）。

若后续要推进，只有两条路：解决注意力服务的主动查询能力，或改成前置摄像头的
自采集方案（功耗与系统限制均需重新评估）。

## 四、仍需人工确认的项

以下项目依赖真实手指操作，adb 注入无法覆盖：

1. 浮窗期间用手指从屏幕左/右边缘侧滑，确认不能返回。
2. 浮窗期间连续按音量下键 5 次，确认立即退出。
3. 浮窗上长按 5 秒，确认立即退出。
4. 浮窗期间按电源键熄屏，再亮屏，确认状态正常（预期：倒计时继续，到点结束）。

## 五、已知风险

- Shizuku 服务若被系统省电策略杀掉，锁定会静默失败，此时只剩浮窗遮罩，
  手势返回可穿透。UI 上已给出「Shizuku 权限：未授权/未运行」提示。
- 锁定期间来电界面可能被压住。当前未做通话状态监听，属于待办项。

## 六、第二轮反馈修复

### 1. 紧急脱出后变成锁屏

**根因不是解锁逻辑，而是浮窗没有保持屏幕常亮。** 浮窗窗口此前没有
`FLAG_KEEP_SCREEN_ON`，20 秒倒计时加上用户操作时间很容易超过系统屏幕超时，
屏幕在浮窗存续期间就已熄灭。浮窗正常移除后露出的是锁屏，因此看起来像「退出后进了锁屏」。

修复：浮窗窗口加 `FLAG_KEEP_SCREEN_ON`。这是窗口标志而非 WakeLock，窗口移除即失效，
不存在常驻唤醒源。

实测：浮窗结束后 `mWakefulness=Awake`，前台仍为原 Activity，锁定状态回到 `NONE`。

### 2. 移除长按 5 秒脱出

实测长按 5 秒无响应，松手后偶发回到锁屏，可靠性不足；且与音量键通道功能重复。
已删除该通道及相关触摸计时逻辑，紧急脱出只保留音量下键连按 5 次。

### 3. 新增「暂停活动」按钮

浮窗是全屏遮罩，不会让下层应用暂停，视频与音频仍在播放。新增按钮：

- 位置：倒计时数字下方，尺寸 168×62dp，约为数字的一半。
- 行为：点击后发送媒体暂停键，按钮文字变为「继续活动」并降低透明度；再点一次恢复。
- 浮窗以任何方式结束（自然倒计时、紧急脱出）都会在移除窗口前自动恢复播放。
- 实现：优先 `AudioManager.dispatchMediaKeyEvent`，失败降级为 Shizuku 注入按键。
  没有活动媒体会话时按键被系统忽略，不产生副作用。

## 七、方案回退：放弃 LockTask（关键）

### 现象

加入 `FLAG_KEEP_SCREEN_ON` 后，浮窗结束仍停在锁屏，且解锁后原应用在后台。

### 根因

`isKeyguardShowing=true` 在浮窗结束后恒为真。原因是 **`am task lock` 内部会调用
`WindowManagerService.lockNow(null)`**，在锁定任务的同时把屏幕锁上。设备设置了密码锁，
`wm dismiss-keyguard` 对已锁定的设备无效（实测执行后 `isKeyguardShowing` 仍为 true），
因此锁定后无法自动恢复。这是系统行为，无 root 无法绕过。

补充：`FLAG_KEEP_SCREEN_ON` 对 `TYPE_ACCESSIBILITY_OVERLAY` 窗口不生效
（浮窗期间 `mStayOn=false`，窗口 attrs 中无 keepScreenOn 标志），需改用限时 WakeLock。

### 备选方案验证（均失败）

| 方案 | 结果 |
|---|---|
| `am task focus <taskId>` | 打印 "Setting focus to task"，界面不动 |
| `am start -n <组件> --activity-reorder-to-front` | 被 HyperOS 后台弹出限制拦截，界面不动 |
| `wm dismiss-keyguard` | 有密码锁时无效 |
| 切三键导航 + 无障碍拦按键 | 可行，但导航栏样式会变，且 adb 注入按键绕过无障碍过滤层，无法自动验证 |

### 最终方案

**全屏遮挡 + 切走即重置顶**：

1. 不做任何锁定，浮窗以无障碍 overlay 覆盖全屏。
2. 监听 `TYPE_WINDOW_STATE_CHANGED`，前台换到别的应用就把浮窗重新挂载
   （`removeViewImmediate` + `addView`）压回最上层，节流 600ms。
3. 浮窗期间持有限时 WakeLock（`SCREEN_BRIGHT_WAKE_LOCK`，20+15 秒自动过期），
   确保全程可见。

实测：手势上滑回桌面后，屏幕上仍是全屏浮窗（倒计时 16 秒），用户实际无法操作设备；
浮窗结束后 `isKeyguardShowing=false`，不再锁屏。

### 结论

手势拦截在不锁屏的前提下无法实现，这是平台限制而非实现缺陷。现方案保留了
「20 秒内用户看不到也操作不了原应用」的实际效果，代价是原应用会被切到后台。
